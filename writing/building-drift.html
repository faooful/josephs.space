Writing

Building Drift, a small tool for keeping a design system from wandering off.

Impulse

I wanted something that would notice when a codebase started quietly wandering away from its own design system.

Not a style guide nobody opens. Not a big audit you run once and forget about. Something smaller than that: a tool that sits next to the code, watches what actually gets merged, and speaks up when it matters.

That was the impulse behind Drift.

It is a CLI and a GitHub Action, and its whole job is keeping a design system from drifting. Which is also why the logo is an animated ASCII car drifting across the terminal. I'll be honest, that part was not strictly necessary.

Drift

The car is doing most of the marketing. The rest is a handful of commands.

Premise

In Scaling designer taste I wrote about the problem with making a markdown file the source of truth for a design system. You create another thing to maintain, and it goes stale.

Drift comes at it from the other side. Instead of writing the system down and hoping the code follows, it looks at the code that actually got merged. A merge is a decent signal that someone meant it.

Start

The first command is drift start. It sets up the rules for a repo, so there is something to check against.

After that, drift check lints the code against those rules. That part is fairly ordinary on purpose. A linter is a familiar shape, and I wanted Drift to feel like something you already know how to live with.

Baseline

The part I cared about most was not making every existing problem someone's problem on day one.

So pull requests fail by default only on new findings, measured against a baseline. Whatever was already there stays visible, but it doesn't block the work. If a change adds new drift, the check says so. If it doesn't, it gets out of the way.

Most codebases already have some drift in them. Pretending otherwise just teaches people to ignore the tool.

Suggest

drift suggest is the bit that learns. It looks at merged history and proposes tokens and rules from it.

I like that direction. It turns what the team actually shipped into a starting point, rather than a spec written up front. You still decide what becomes a rule.

Library

drift library serves or exports a local design-system site. It has Foundations, Components with real renders, Rules, and a Timeline of merged PRs.

The real renders matter. A component page that shows the actual component is a lot more trustworthy than a screenshot someone took months ago.

The Timeline is probably my favourite part. It gives the design system a history, not just a list of what is allowed.

Setup

Getting it into a repo is meant to be boring. drift setup adds a one-file workflow to any repo. drift remove takes it out again.

That second command matters more than it sounds. A tool is much easier to try when it is just as easy to undo.

Team

I built Drift with my team of AI bots over the past few days.

That is still a slightly strange sentence to write. But it is how it happened: lots of small steps, each one reviewed, with me deciding what stayed.

Where it landed

Drift started as a way to catch design-system drift and became a small set of commands: start, check, suggest, library, setup, remove. And a car.

The interesting part was not the linting. Plenty of tools can lint. The interesting part was making the check fair to a codebase that already has a history, and letting that history suggest the rules instead of the other way round.

It is still early, and the repo is private for now.

But there is a little car drifting across my terminal, and a design system that is a bit harder to wander away from.

That feels like enough for now.
